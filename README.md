# Industrial AI Platform — Machine Health & Maintenance Dashboard

**Predict • Prevent • Optimize**

A production-quality industrial AI monitoring and predictive-maintenance
platform, built for factories, engineering teams and enterprise demonstrations.
It combines a Vite/React dashboard with an internal FastAPI service for machine
failure and sensor-anomaly inference.

> **Scope notice.** Machine failure probability, failure type, sensor anomaly
> score, health, and maintenance recommendation are generated by the trained
> model service. Assistant responses and computer-vision inspections remain
> simulated and are labeled as such.

## Getting Started

```bash
npm install
npm run setup:ml
npm run dev       # dev server (Vite)
npm run build     # production build -> dist/
npm run preview   # preview the production build
npm run typecheck # tsc --noEmit
```

Node.js 18+ and Python 3.10+ are required for local development. `npm run dev`
starts the local ML service on `127.0.0.1:8001`, waits for the trained models to
load, and then starts Vite. If the ML service is already running, it reuses it.
For separate terminals, run `npm run dev:ml` and `npm run dev:app`.

## Deploying on Vercel

The root `vercel.json` deploys the Vite frontend as the public `app` service and
routes all paths to it. The app service rewrites client-side routes to the Vite
entry page so deep links (for example, `/machines`) work when opened directly.
The `ml` service runs the FastAPI inference backend and stays internal. The
public `/api/predict` function in the app service forwards requests through the
`ML_SERVICE_URL` service binding; the browser never receives the internal URL.

For local end-to-end development, start the backend and frontend separately:

```bash
cd ml
python -m pip install -r requirements.txt
python -m uvicorn main:app --host 127.0.0.1 --port 8001
```

In another terminal, run `npm run dev`. The Vite development proxy forwards
`/api/*` to `ML_API_DEV_ORIGIN`, which defaults to `http://127.0.0.1:8001`.
Set `ML_API_DEV_ORIGIN` if the local backend runs elsewhere. In production,
Vercel injects `ML_SERVICE_URL` into the app functions from the service binding.
Only the app is public; the ML service is called by server-side API functions.
Notebook dependencies are listed separately in `ml/requirements-research.txt`.

## Core Product Flows

1. **Predictive maintenance**
   `Simulated Sensor Inputs → /api/predict → Failure + Anomaly Models →
   Health Score → Recommendation → Alerts and History`
2. **Document intelligence / RAG**
   `Document Upload → Knowledge Base → RAG Assistant → Context-aware Answer →
   Source Citation` (simulated from document metadata; API-ready)
3. **Computer-vision quality inspection**
   `Product Image → Inspection → Defect Detection → PASS/FAIL → Quality Analytics`

## What Is Actually Functional

The dashboard is interactive, and machine prediction fields are populated only
from the trained ML service. Demo sensor readings are simulated and marked:
the model input type is automatically inferred from each machine category:
compressors/boilers map to H, conveyors/packaging/labels to L, and other
categories to M. This is a demo mapping, since the model's training codes do not
have a verified one-to-one correspondence with the dashboard's categories.

- Click a machine card → full machine profile with charts and event markers
- **Add Machine** → appears immediately in the list; optional CSV / XLSX / JSON
  historical upload with a validation report, simulated sensor inputs, and
  model-generated health, failure risk, recommendation, and trend entries
- Startup predictions are fetched from the internal service; loading and
  unavailable states never substitute mock health or risk values
- Schedule / edit / complete maintenance → machine maintenance status updates
- Upload documents → appear in the Knowledge Base; the assistant cites them as sources
- Upload a product image → simulated inspection with bounding-box annotation
- Filters, search, threshold changes, alerts and toasts all update live state
- Settings stores reference thresholds; model-provided statuses are not overridden
- Loading, empty, success and error states plus confirmation dialogs for destructive actions

State is persisted to `localStorage` under `iap-state-v3`. Settings → Data
Management can reset the seed dataset or clear the cached state.

## Remaining Simulated Features

Only the following AI features are still simulated:

- Assistant RAG — replace the mock retrieval in `pages/AssistantPage.tsx` with a
  vector-store query (embeddings + document chunks) returning `sources[]`
- Inspection — replace the mock classifier with a vision endpoint returning
  `{ result, defectType, confidence, boxes[] }`

Machine failure probability, failure type, sensor anomaly score, health, status,
and maintenance recommendation already come from the internal FastAPI model
service. The browser calls the public app API; the internal service binding URL
is only used by server-side Vercel functions.
